# Yurun（语润）语音输入架构诊断与重构方案

> **文档性质**：正式架构诊断（经源码逐行核实版）
> **依据**：Yurun 当前源码（v1.0.1，NAS `D:\SynologyDrive\CODING\yurun`）+ 用户提供的 Gemini 诊断 + 水杉（MetasequoiaVoiceInput）项目分析
> **原则**：本文所有"事实判断"均附 `文件:行号` 源码证据，凡无法在源码中证实者标注为"推断/目标"。

---

## 0. 最终结论（先说五句）

1. **Yurun 的 ASR 后端没有从根上做错**——默认路径是真正的 WebSocket 流式 ASR（`sauc_transcribe_stream` + `record_chunks`），不是 Gemini 所判的"VAD 触发式分块批处理"。
2. **Yurun 最大的问题，是把 Streaming ASR 的 Partial Result 浪费掉了**——服务端持续返回中间结果，但代码只攒在 `state["text"]` 里、**不实时回显**。
3. **LLM 流式润色已经做得不错**——`refine_stream()` 是真正的 SSE 流式，`on_delta` 实时驱动 `SendInput` 首字上屏，并非假流式。
4. **真正拉开与水杉体验差距的，是 Windows 输入层**——你用 `SendInput` 模拟键盘提交，水杉类方案用 TSF Composition 把 Partial 变成"正在组合的文字"。
5. **现在不要急着换 ASR**——应保留 SAUC，先"释放 Partial → 建立 Preedit → 最后接 TSF"。

## 1. 源码核实：当前真实架构

### 1.1 存在两条录音路径（关键校准点）

源码里**不是只有一条**路径，Gemini 和你那份草案都略有简化。实际分派逻辑在 `main.py:299`：

```python
if cfg.get("asr_provider") == "sauc":
    self._rec_thread = threading.Thread(
        target=self._record_job_sauc, args=(stop, cfg), daemon=True)
else:
    self._rec_thread = threading.Thread(
        target=self._record_job, args=(stop,), daemon=True)
```

- **默认 = 真流式**：`config.py:31` 写死 `"asr_provider": "sauc"`，所以开箱即走 `_record_job_sauc` → `record_chunks()` + `sauc_transcribe_stream()`。**你的"Yurun 是流式"判断对**，但前提是用户没切到 cloud/local。
- **cloud/local = 批处理**：走 `_record_job` → `record_to_file()` 录成整段 WAV → `_transcribe()` 再发识别。这是另一条独立链路。

> **校准**：说"Yurun 是流式"对默认配置成立；若用户把 provider 切成 cloud 或 local，则确实回到"整段录完再识别"的批处理模式。Gemini 之所以误判，极可能是只看到了 `record_to_file` 这个批处理函数。

### 1.2 SAUC 真流式证据（无可争议）

`src/sauc_asr.py:223` `sauc_transcribe_stream()`：

```python
ws = websocket.WebSocketApp(endpoint, header=headers, on_open=..., on_message=..., ...)
threading.Thread(target=ws.run_forever, ...).start()
...
for chunk in chunk_iter:                       # ← 录音生成器边产出边发
    ws.send(_build_audio_packet(chunk, is_last=False), opcode=0x2)
ws.send(_build_audio_packet(b"", is_last=True), opcode=0x2)   # ← 松手才发 FLAG_LAST
if not state["done"].wait(timeout=timeout):
    state["error"] = "识别超时"
```

- 协议：自定义 4 字节头 + gzip 二进制帧（`_make_header`、`_build_audio_packet`）。
- 音频参数：`sauc_asr.py:72` `rate=16000 / bits=16 / channel=1`；`request.model_name="bigmodel"`，`enable_itn/enable_ddc/enable_punc/show_utterances` 全开（`sauc_asr.py:79-84`）。
- `record_chunks` 是流式生成器：`recorder.py:63` `def record_chunks(stop_event=None, on_level=None, chunk_ms=100, max_seconds=90.0)`，`while True: ... yield (data*32767).astype("int16").tobytes()`。
- 只有在用户松手（stop_event）时才停止 yield、发 `FLAG_LAST`（`sauc_asr.py:310`），**不存在"VAD 切断后一次性上传大块"**。

### 1.3 Partial 被浪费的证据（核心缺口）

`sauc_asr.py:260` `_on_message`：

```python
if parsed.get("text"):
    state["text"] = parsed["text"]        # ← 中间结果只写进内部变量
flags = (message[1] & 0x0F) if len(message) > 1 else 0
if flags & 0b0010:                        # ← 仅 FLAG_LAST 最终结果才 done
    state["done"].set()
```

函数 docstring 自己写明（`sauc_asr.py:231`）：

> "录音期间服务端边听边返回中间结果（**这里只攒着、不回显，避免文字跳变**），松手后发尾包 → 等 FLAG_LAST 最终结果 → 返回最终文本。"

也就是说：**Partial 已经稳定产生，但被主动丢弃了 UX**。这正是诊断里"Streaming Backend ≠ Streaming UX"的命门。

### 1.4 LLM 流式润色证据（已做对）

`src/refiner.py:258` `refine_stream()`：

```python
body = json.dumps({"model": model, "stream": True, ...,
                   **({"thinking": {"type": "disabled"}} if disable_thinking else {})})
...
for raw_line in resp:                    # ← 真 SSE 流式
    ...
    delta = obj["choices"][0]["delta"].get("content")
    if delta:
        accumulated += delta
        started = True
        if on_delta: on_delta(delta)     # ← 每片回调
```

`main.py:725` `_refine_stream_and_paste()`：

```python
def on_delta(seg):
    if round_id is not None and round_id != self._round_seq: return
    self.ui_q.put(("type_partial", seg))   # ← 经 UI 队列投递，主线程 SendInput 逐字上屏
result = refine_stream(text=..., on_delta=on_delta)
```

- `disable_thinking=True`（`refiner.py:299`）——与你从水杉学到的"关思考提速"完全一致。
- 首字即上屏：`_refine_stream_and_paste` 在 `on_delta` 第一次被调用时就往目标应用打字。

### 1.5 计时口径：日志里的"识别耗时"含录音时间（关键反证）

`sauc_transcribe_stream` 是**阻塞式**的：它的 `for chunk in chunk_iter` 一直跑到 `record_chunks` 生成器耗尽（= 用户按住热键的整个时长）。计时点在 `main.py:632/642`：

```python
t_asr0 = time.time()
text = sauc_transcribe_stream(record_chunks(stop, ..., max_seconds=90), ...)
log.info("SAUC 识别耗时=%.2fs", time.time() - t_asr0)
```

因此这个 `SAUC 识别耗时` = **建连 + 整个录音过程 + 持续发 PCM + 持续收 Partial + 松手 + 等 FLAG_LAST 最终结果**，**绝非纯服务器处理时间**。

> 这直接推翻了 Gemini 的"6.5s 是 ASR 刚性物理底线"——若用户典型说话 5~6 秒，日志自然显示 ~6.5s，其中服务器 Final 延迟仅约 0.6~1s（见 `sauc_asr.py:312` 注释："松手后最终结果已经很快（真实场景约 0.6~1s）"；模块头注释 `sauc_asr.py:11`："5 秒音频约 300-400ms 返回"）。

### 1.6 当前完整链路（默认 sauc 模式）

```
用户按住热键
  → _on_hold_start (main.py:288)  [asr_provider==sauc]
  → _record_job_sauc (main.py:619)
       → record_chunks() 流式采 PCM (recorder.py:63)
       → sauc_transcribe_stream() 边发边收 (sauc_asr.py:223)
            ├─ Partial → state["text"]（不显示）
            └─ FLAG_LAST → 返回 Final Text
  → _after_transcribe (main.py:649)
       → strip_numeric_trailing_punct / apply_local_replace
       → 短句(bypass ≤15字) → 直接 paste 原文
       → 否则 → _refine_and_paste → _refine_stream_and_paste (main.py:725)
            → refine_stream() SSE 流式 → on_delta → type_partial → SendInput
```

## 2. 对 Gemini 诊断的逐条纠正

### ✅ 正确且核心的判断

| Gemini 判断 | 源码佐证 |
|---|---|
| ASR 草稿应毫秒级上屏、LLM 后台流式精修、互不阻塞 | `refine_stream` 已流式；Partial 本可上屏但未接 |
| Partial 应立即进入用户视野 | `sauc_asr.py:274` 已有 Partial，仅缺 UI 出口 |
| SendInput 不是最终答案（竞态/闪烁） | 当前确为 `SendInput` 逐字模拟（`main.py:822` `_do_type`） |
| TSF 是最终目标架构 | 见 Phase 3 |
| Python 主程序 + TSF Bridge（IPC 到 C++/COM） | 架构合理，无需重写 Yurun |

### ❌ 错误判断（附源码反证）

**错误 1：Yurun 是 VAD 触发式分块批处理**
- 反证：`config.py:31` 默认 `sauc`；`main.py:299` 据此走 `_record_job_sauc` → `record_chunks`(流式生成器) + `sauc_transcribe_stream`(WebSocket 边发边收)。"切除批处理改成流式"对已默认配置是**已完成的工作**。
- 根源：Gemini 大概率只看到 `recorder.py:15` 的 `record_to_file()`（批处理），没看到同文件 `recorder.py:63` 的 `record_chunks()`。

**错误 2：最大 60 秒 = VAD 缓冲到 60s 一次性上传**
- 反证：流式路径用 `record_chunks(max_seconds=90)`（`recorder.py:63` 默认值，且 `_record_job_sauc` 显式传 `max_seconds=90`，`main.py:634`）。它是**逐 chunk 直发 WebSocket**，不是"60 秒缓存一次上传"。`record_to_file` 的 `max_seconds=60` 是**批处理函数**的默认值，与流式路径无关。

**错误 3：6.5s 中位数是 ASR 刚性物理底线**
- 反证：计时含录音时长（§1.5）；服务器 Final 延迟约 0.6~1s（`sauc_asr.py:11,312`）。6.5s ≈ 用户说话时长 + 收尾，不能直接等价于 ASR latency。

**错误 4：ASR→LLM 完全串行是"错误架构"**
- 澄清：从"用户拿到最终润色文本"视角确实是串行（`Final ASR → LLM`）。但**你的 LLM 流式实现本身没错**——`refine_stream` 已是 SSE 流式 + `on_delta`。真正缺的是"ASR Partial"与"LLM Final Refinement"**并行共存**，而非"LLM 要不要流式"。

## 3. 真正的问题定义

> **Yurun 不是"ASR 做错了"，而是"已经有一个正确的 Streaming ASR，却用传统的 Batch 输入法方式消费它"。**

```
                后端
                 ↓
        ┌─────────────────┐
        │ Streaming ASR   │ ← 做对了（sauc_transcribe_stream）
        │ Streaming LLM   │ ← 做对了（refine_stream + on_delta）
        └────────┬────────┘
                 │
                 ▼
             传统输入层（SendInput 整段/流式提交）
                 │
                 ▼
              目标应用
```

目标应升级为：

```
                后端
                 ↓
        ┌─────────────────┐
        │ Streaming ASR   │
        │ Streaming LLM   │
        └────────┬────────┘
                 │
                 ▼
           TSF Composition（Partial 成为输入法状态）
                 │
                 ▼
              目标应用
```

**一句话**：差距不在"有没有 Streaming ASR"，而在"Partial 有没有成为输入法状态的一部分"。

## 4. 重构方案（Phase 0 → 3）

> 原则：**先测量、再释放、后替换**。前两个阶段不动输入层，只在现有 Python 内验证；第三阶段才引入 TSF Bridge。

### Phase 0：修正测量（什么都不改逻辑，只加时间戳）

当前 `SAUC 识别耗时` 把录音时间算进去了，无法判断 SAUC 到底慢不慢。建议在 `sauc_transcribe_stream` 与 `_record_job_sauc` 中加 7 个时间戳：

| 标记 | 位置（建议插入点） | 含义 |
|---|---|---|
| T0 | `sauc_transcribe_stream` 函数入口 | WebSocket 建连前 |
| T1 | `_on_open` 内 `state["opened"].set()` 前 | 连接建立 |
| T2 | `for chunk in chunk_iter` 首次 `ws.send` 前 | 第一包 PCM |
| T3 | `_on_message` 首次 `parsed.get("text")` 为真时 | **首个 Partial** |
| T4 | `for` 循环结束（最后一次 `ws.send`） | 最后包 PCM |
| T5 | `ws.send(..., is_last=True)` 后 | 发 FLAG_LAST |
| T6 | `_on_message` 收到 `FLAG_LAST`（`state["done"].set()`） | Final 结果 |
| T7 | 函数返回前 | 关闭 |

派生指标：
- **首字延迟** = T3 − T0（用户开始说话后多久看到第一个 ASR 结果）
- **松手→Final 延迟** = T6 − T5（用户感知的"说完了为啥还没结束"）
- **纯收尾延迟** = T6 − T4

跑 100 次短句 + 100 次长句，得 P50/P90/P99。到那时才能确切回答"SAUC 慢不慢"。

### Phase 1：释放 Partial（低风险验证）

把 `_on_message` 里 `state["text"]` 的更新，额外经 `ui_q` 投到一个**测试浮窗**（独立 Tk 顶置窗口，不抢焦点、不 SendInput、不碰 TSF）：

```python
# sauc_asr.py _on_message 内，state["text"] 更新后：
if parsed.get("text"):
    state["text"] = parsed["text"]
    if state.get("on_partial"): state["on_partial"](state["text"])   # 新增回调
```

`_record_job_sauc` 传入 `on_partial=lambda t: self.ui_q.put(("partial_preview", t))`，由主线程浮窗显示。

目标：**证明你自己的 SAUC 已经能做到"说一句、文字跟着出来"**。这一步纯粹验证 Partial 稳定性，不做任何提交。

### Phase 2：伪 Preedit（SendInput 增量，验证稳定性）

暂不引入 TSF，但不再把每个 Partial 当新文本整体输入。而是比较 `old_partial` 与 `new_partial`：
- 共同前缀保留，只把差异部分 SendInput 进去；
- 若前缀被改写（如"今天天气"→"今天的天气"），撤销共同尾部再重输。

意义：验证 ASR Partial 实际稳定性，为 Phase 3 积累经验。**风险**：用户移动光标/切窗口时"先删后打"会乱，需加焦点状态机，发现不稳定即回退 Phase 1 浮窗。

### Phase 3：TSF Bridge（最终目标）

```
              Yurun Python
        ┌──────────┼──────────┐
       ASR        LLM        UI
        └─────┬─────┘
              IPC
               ▼
        ┌──────────────┐
        │ TSF COM Bridge │  (C++/COM，独立进程)
        └──────────────┘
               ▼
        Windows TSF → Chrome/Edge/Word/微信...
```

Bridge 只负责：`start_composition / update_text / end_composition / commit / cancel`。不承担 ASR/LLM。这样才能在第三方输入框里出现**真正带下划线的 inline preedit，且可原位修改**——即水杉"言出法随"的本质。

---

## 5. 当前可立即做的实验（最小成本）

1. **只做 Phase 0 + Phase 1**：加时间戳 + 把 Partial 打到测试浮窗。**不改任何提交逻辑、不碰 TSF、不碰 SendInput 主路径**。
2. 若实测 `首个 Partial 100~300ms`、松手→Final `<1s`、Partial 稳定更新 → 整个方向就清楚了：**ASR 根本没想象中慢，瓶颈是"Partial 没被消费"**。
3. 验证通过后再进入 Phase 2（伪 Preedit）与 Phase 3（TSF Bridge）。

## 7. 一句话诊断（定稿）

> **Yurun 已经有一个正确的 Streaming ASR 与一个正确的 Streaming LLM，却用传统的 Batch 输入法方式（SendInput）消费它们；最大的浪费是 ASR 的 Partial Result 从未进入用户体验。下一步不是换 ASR，而是释放 Partial、建立 Preedit，最终以 TSF Bridge 升级为 Windows 真正的实时语音输入法。**
